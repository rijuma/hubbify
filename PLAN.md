## Goal

Fix the findings of the security audit of hubbify that belong to this repository. Finding numbers are the audit's.

- (5, hubbify half) Every action in `.github/workflows/ci.yml` and `.github/workflows/release.yml` is pinned by commit SHA.
- (8) `just` recipes that turn a server/context name into a path under `servers/` reject names such as `../docs`.
- (2) The internet-facing Caddy container no longer mounts the Docker socket; it reads the Docker API through a read-only socket proxy on a private network, locally and remotely alike. A label such as `caddy.reverse_proxy: unix//var/run/docker.sock` no longer reaches the daemon, and no write (POST) request can reach it through the proxy stack.
- (10) The Caddy container runs with all capabilities dropped except `NET_BIND_SERVICE`, and with `no-new-privileges`.
- (3) The docs and `servers/_template/server.env` ask for one Cloudflare token per server, scoped to that server's zones, and `docs/project-contract.md` states that labels are a trusted channel, so the contract holds only for trusted deployers.
- (9) `docs/architecture.md` no longer claims secrets never rest on the server's disk.
- (11) `docs/architecture.md` (Isolation) and `docs/project-contract.md` state the limits of the shared `proxy` network.
- The CI smoke test still passes; each change ships with a changeset.

Out of scope: building option B (operator-owned deploys, per-project ingress networks); every change to `../hubbify-template`; GitHub repository settings; moving servers.

## Decisions (do not reopen)

- Same VPS is kept. Option B (operator-owned deploy: a third party only pushes an image; compose, labels, secrets and SSH key live in a deploy repo the operator owns) will be offered later as an opt-in path, not enforced. First-party projects keep using hubbify and the template as they are. This plan documents the trusted-deployer model; it does not build option B.
- Finding 2 uses a socket proxy, not caddy-docker-proxy's controller/server split: one extra container and one env var (`DOCKER_HOST`), no change to how Caddy is configured. Image: `tecnativa/docker-socket-proxy`, pinned by version tag and digest.
- Residual risk of finding 2, accepted and documented in step 4: Caddy must reach the socket proxy, so someone who can set labels can still point `caddy.reverse_proxy` at it and read (never write) the Docker API, container env included. That is part of "labels are a trusted channel"; closing it belongs to option B.
- Finding 8 validates only the recipes where the name becomes a path (`firewall`, `server-create`, `server-remove`, `remote-up`, `remote-logs`) plus `upgrade`, which calls two of them after changing the server. `ssh` and `cleanup` pass the name only to `ssh` on the operator's own machine and stay as they are.
- Finding 11 is documentation only in this plan; per-project ingress networks belong to the option B work.
- The template-side findings (1, 4, 6, 7 and the template half of 5) are planned in `../hubbify-template/PLAN.md` and are not open work for this plan: no step here touches that repo, and the close-out does not carry them into `FOLLOW-UPS.md`.
- Manual follow-up for the user, GitHub settings (finding 12), not a step: a ruleset on `main` in both repos; require SHA-pinned actions; turn off "Allow GitHub Actions to approve pull requests" in hubbify.
- `prettier --check` is not on the verify line: `proxy/compose.yml` and `.github/workflows/release.yml` already fail it on `main`, and reformatting them is not part of this plan.
- Changesets are written by hand as `.changeset/<name>.md` (front matter `"hubbify": patch` or `minor`, then a short paragraph; see `.changeset/guard-labels.md`), since `pnpm changeset` is interactive.

- [ ] **3. Put a read-only socket proxy in front of the Docker socket and harden the Caddy container** — Today `proxy/compose.yml` mounts `/var/run/docker.sock` into the `caddy` service, the only container on 80/443; `:ro` does not restrict the API (confirmed in the audit: a container labelled `caddy.reverse_proxy: unix//var/run/docker.sock` exposed the API and a POST reached the daemon). Change `proxy/compose.yml` (the base file, so local and remote get the same stack; `proxy/compose.remote.yml` should need no change) to: (a) add a service named `socket-proxy` running `tecnativa/docker-socket-proxy` pinned by version tag and digest, which mounts the socket read-only, publishes no ports, restarts `unless-stopped`, and allows only GET on what caddy-docker-proxy needs (`CONTAINERS=1`, `NETWORKS=1`, `INFO=1`, with the image's defaults for events, ping and version; `POST=0`); enable another section only if the Caddy logs show a 403 for it without Swarm, and say which in the changeset; (b) add a private network declared `internal: true` in this compose file that only `socket-proxy` and `caddy` join; `socket-proxy` joins nothing else, in particular not the external `proxy` network; (c) on `caddy`, remove the socket volume, set `DOCKER_HOST=tcp://socket-proxy:2375`, keep `CADDY_INGRESS_NETWORKS=proxy` (Caddy now has two networks and must keep routing over `proxy`), and start after `socket-proxy`; (d) on `caddy`, add `cap_drop: [ALL]`, `cap_add: [NET_BIND_SERVICE]` and `security_opt: ['no-new-privileges:true']` (checked while planning: the current proxy image binds port 80 with exactly these options). In `.github/workflows/ci.yml`, keep the whoami smoke test as it is and add, after it, assertions that inside the `caddy` container `/var/run/docker.sock` does not exist and that a POST to `http://socket-proxy:2375/containers/create` is refused (the Caddy image is Alpine: busybox `wget --post-data=x`). In `docs/architecture.md`, update "The big picture" (mermaid: Caddy talks to the socket proxy on a private network, the socket proxy holds the socket) and "Reverse proxy" (the caddy-docker-proxy bullet, the build diagram's "read from docker socket" edge, and a short paragraph on the socket proxy: read-only, GET-only sections, private network, why, and the dropped capabilities), describing the final state with no history. The recipes `logs` and `remote-logs` keep following the `caddy` service. Before finishing, run the CI sequence locally: `just up`, start a `traefik/whoami` container on `proxy` with the two labels from `ci.yml`, confirm `curl -fsk --resolve whoami.localhost:443:127.0.0.1 https://whoami.localhost` answers, check `docker compose -f proxy/compose.yml logs caddy` for Docker API errors, then remove the whoami container (leave the proxy running: the user's local projects use it). Add the changeset `.changeset/socket-proxy.md` (minor), noting that servers pick the change up with `just upgrade <server>` or `just remote-up <server>`. Read: Goal (findings 2 and 10), Decisions (finding 2, two bullets), `docs/architecture.md` → The big picture, Reverse proxy; `AGENTS.md` → Hard rules. Depends on: 1. - [ ] **4. Document the trust model: labels, the Cloudflare token, secrets on the server, the shared network** — Docs only, describing the final state (no history, no changelog wording). (a) `docs/project-contract.md`: add a section headed exactly `## Trust model`, placed after "The rules", saying the contract holds only for trusted deployers and why: labels are a trusted channel, so anyone who can deploy to the server (set labels on a container) can claim any domain, including one another project serves; can read the proxy's environment through the allowed labels (`caddy.respond` and `caddy.header.<Name>` accept Caddy placeholders such as `{env.CLOUDFLARE_API_TOKEN}`); can read container env with `docker inspect` over their deploy key's Docker access; and can point `caddy.reverse_proxy` at the socket proxy to read (never write) the Docker API.
