## Decisions (do not reopen)

- Order: the per-server Caddyfile work lands before the firewall work, because both edit `proxy/Caddyfile.remote`.
- Per-server Caddyfile delivery: baked into the proxy image. `proxy/compose.remote.yml` adds `build.additional_contexts: { server: ../servers/${SERVER_NAME}/caddy }`, a folder that holds only the `Caddyfile`, because BuildKit uploads a whole local context folder to the building daemon (only `.dockerignore` filters it, not the `COPY` lines), so pointing it at `servers/<name>/` would upload `server.env` to the server and keep it in its build cache; `remote-up` runs `mkdir -p servers/<name>/caddy` first so servers without one still build; `proxy/Dockerfile` declares a default stage named `server` that provides nothing, so local builds (no additional context) and servers whose `caddy/` folder has no `Caddyfile` still build. At build time an intermediate stage appends that context's `Caddyfile` (when present) to the end of `/etc/caddy/Caddyfile.remote`, and only the resulting file reaches the final image (never `server.env`). No `import`: caddy-docker-proxy v2.12.0 parses the base Caddyfile with its own lexer and does not expand `import`, so an imported `docs.smu.ar` block would not merge with the label-generated `docs.smu.ar` site and Caddy would reject the duplicate ("ambiguous site definition"); appended blocks are merged by caddy-docker-proxy like any other base-Caddyfile block. The file is `servers/<name>/caddy/Caddyfile` (gitignored local state, like `server.env`); it replaces `proxy/Caddyfile.remote` as the place for per-site extras (auth, headers, redirects). No label allowlist.
- Sibling-name collision on the shared `proxy` network (FOLLOW-UPS item 1): fixed as a contract rule only. The optional deploy-time warning would live in each project's deploy (hubbify-template), not in hubbify; left out.
- The parked `docs.smu.ar { basic_auth … }` block (git stash "docs.smu.ar basic_auth") moves into `servers/pachuca/caddy/Caddyfile`, not the shared base; the stash is dropped afterwards. Redeploying pachuca (`just remote-up pachuca`) is the user's call, not a step.
- Firewall persistence: a block marked `# BEGIN hubbify` / `# END hubbify` in `/etc/ufw/after.rules` and `/etc/ufw/after6.rules` (its own `*filter` … `COMMIT` section feeding `DOCKER-USER`), then `ufw reload`. With `CLOUDFLARE_ONLY=true` the recipe aborts if ufw is not active (the operator enables ufw first).
- Without `CLOUDFLARE_ONLY=true` the recipe removes hubbify's block if present (reloading ufw only when it removed something), so opting out is flip the flag and rerun. Derived from that answer: the inactive-ufw abort applies only to opted-in servers, so `just upgrade` keeps working on servers without ufw.
- Drop rules must only hit inbound published-port traffic (DNATed connections, e.g. `-m conntrack --ctstate DNAT --ctorigdstport 443`), never the containers' own outbound 80/443 traffic; established/related traffic is allowed first.
- Real client IP in Caddy: the `github.com/WeidiDeng/caddy-cloudflare-ip` module in `proxy/Dockerfile` (`trusted_proxies cloudflare`, self-refreshing) plus `client_ip_headers CF-Connecting-IP`, on every remote server (trusting Cloudflare's ranges is safe without the firewall too).
- Visitor-IP header for projects: `CF-Connecting-IP`, documented as trustworthy only on `CLOUDFLARE_ONLY` servers.
- Not a step: the live acceptance in `firewall-security.md` → Acceptance (curl from a non-Cloudflare IP, reboot, `systemctl restart docker`) needs a real server; the user runs it by hand after the plan.
