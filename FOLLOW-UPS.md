# Follow-ups from Plan: security audit fixes (hubbify side)

Issues noticed while implementing and reviewing the plan; none were in
scope. Review, delete what does not matter, then `/plan-steps FOLLOW-UPS.md`.

- `justfile:171` (`_server-name`) and `docs/architecture.md:180` — the name check accepts `local`, while the docs paragraph that describes the check says `local` is not available as a server name; step 2 also removed the only reserved-name guard (`_template`) because the pattern covers it, and nothing covers `local` — `just server-remove local` deletes the untracked `servers/local/` (the local proxy's Caddyfile extras, not recoverable from git) and `just remote-up local` would build a server's proxy from that folder (step 2, close-out)
- `docs/project-contract.md:99` (Trust model) — the list of what a deployer can do stops at reading env with `docker inspect` and reading the Docker API through the socket proxy, but the deploy key's Docker access over SSH is root-equivalent on the server (bind mounts, privileged containers), so the read-only socket proxy limits only what a label can do through Caddy, not what a deployer can do — an operator deciding who gets a deploy key reads the section as a weaker grant than it is (step 4)
- `.github/` and `proxy/compose.yml:36` — the plan pinned every action by SHA and the socket-proxy image by digest, but the repo has no Dependabot or Renovate config for `github-actions` or docker, so the pins never receive security updates unless someone bumps them by hand (the socket-proxy pin is `v0.5.0` because `v0.6.0` had no Docker Hub image yet) — the pinning meant to reduce supply-chain risk freezes known vulnerabilities in place (steps 1, 3)
- `docs/architecture.md:348` (DNS, planned) — says the Cloudflare API token "lives on the client/CI only, never on the server", while TLS and the trust model now state that a Zone → DNS → Edit token sits in the proxy container's env and every deployer on the server can read it — the two sections contradict each other about whether a DNS-edit token is on the server (step 4)
- GitHub repository settings (audit finding 12; manual task for the user, not a step, recorded only in the deleted plan's Decisions) — a ruleset on `main` in both repos, require SHA-pinned actions, and turn off "Allow GitHub Actions to approve pull requests" in hubbify — without the "require SHA-pinned actions" setting nothing stops a later workflow edit from going back to tags (close-out)
