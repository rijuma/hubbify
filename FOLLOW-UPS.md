# Follow-ups from the first smu-platform deploy to pachuca (2026-10-10)

Issues found while deploying `smu-platform` (`smu.ar`) behind the pachuca proxy; none were fixed here. Review, delete what does not matter, then `/plan-steps FOLLOW-UPS.md`.

- `docs/project-contract.md` and the shared `proxy` network — Docker gives every container its service name as an alias on each network it joins, so every project's `web` service answers to `web` on `proxy` (six on pachuca today: cvcar, rigolidev, tembo-prod, tembo-stg, psicoenlace, pichangacomar); a project whose web-facing service proxies to a sibling by a generic name (smu's gateway did `reverse_proxy web:4321`) gets another project's container at random — on smu.ar it gave 401s, 404s and refused connections that never show up locally; fix: a contract rule that a service on `proxy` reaches its siblings only by project-unique names (an alias on the project's default network, as smu-platform now does with `smu-web`/`smu-api` in `infra/compose.yml`), optionally a deploy-time check that warns when a project's `proxy` service upstreams to a name that also resolves on `proxy`
- `docs/project-contract.md` rule 3 and `proxy/Caddyfile.remote` — the only sanctioned place for config beyond domain + port (auth, headers, redirects) is one base Caddyfile baked into the proxy image that every server runs, so a `smu.ar { basic_auth … }` block would be served by every server (noovat-vps would also request a certificate for smu.ar) and adding or removing it means rebuilding and restarting the proxy in front of every site on the server; smu-platform worked around it with a gate inside its own gateway (`envs/prod/compose.yml` `preview-auth` config imported by `infra/Caddyfile`); fix: per-server or per-project extra config (e.g. `servers/<name>/Caddyfile` imported by the remote base, or an import glob fed by a compose config), or a short allowlist of label directives such as `basic_auth`
